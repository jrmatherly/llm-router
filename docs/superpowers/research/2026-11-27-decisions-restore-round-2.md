## F-RESTORE-1. ZCode's model cache when `v2/config.json` is deleted

1. **Re-measure.** Confirmed (run). With a user cache and `v2/config.json` deleted during the takeover, the switch-off is ok and the cache keeps LLM Router's entry and its three model references. This is the new test `a ZCode cache gives LLM Router's entry back...`, which fails on `v9.1.0` with providers `['other', 'llm-router']`.
2. **Does ZCode itself delete or rewrite either file?** ZCode is not installed (`command -v zcode` found nothing, no app under `/Applications`). Installing it means the desktop download from zcode.z.ai or its CLI installer, which writes `~/.zcode/runtime` and `~/.local/bin` (read, ZCode `README.en.md`). I stopped there. Its source is public, Apache-2.0, at `github.com/zai-org/ZCode`, read at `a4b4445` of 2026-11-23, CLI package 0.18.0. What it says (read):
   - `docs/bots.md`. Old `bots-model-cache*.json` files are no longer read or written. A design note (`docs/working-memory/provider-refactor/steps/todo-69-...md`) says the Bot Model Cache repository was deleted and the old cache is left untouched.
   - The same note and `packages/provider-node/src/personal-provider-config-repository.ts`. Providers now live in `v2/provider_config.json`. `v2/config.json` is a one-time upgrade input. It is imported only when `provider_config.json` does not exist, and the repository neither rewrites it nor backs it up. The CLI imports `cli/config.json` providers the same way (`legacy-cli-personal-provider-config-importer.ts`).
   - `docs/settings-storage-management.md`. ZCode's storage cleanup lists `v2/bots-model-cache*.json` and `v2/*.json` as not deletable.

   So ZCode deletes neither file, and the trigger stays a person deleting `v2/config.json` (read). The cost round one weighed, ZCode opening with LLM Router's model selected, needs a ZCode that still reads the cache. The current source does not, so on a current install the leftover entry is inert (inferred from source, not run). Whether the shipped desktop app matches that source was not checked.
3. **Prototype of the apply-time record (run).** `globalZcodeWriter` adds the ids LLM Router wrote to the cache's existing written record (`zcodeOwnedIds`), and `zcodeOwnedProviderIds` reads that record when `v2/config.json` is gone. The record is cleared with the cache's restore, as today. The change is `service.ts` +25 −4 and `codex-config-strip.ts` +1, with one test of 13 lines. `npm run test:core` passed, 2551 tests and none failed (run). Patch `f-restore-1-proto.patch`.
4. **Differential run (run).** The batch 10b harness, extended with a user entry `llm-router` and a user `lastUsed` under `llm-router` in the original cache, a second ZCode profile `zc-two` and a `swap` step, and the deletion of any of the three files. Two seeds of 2000 scenarios each, the same scenarios through `v9.1.0` and the prototype. Steps are applies, saves, edits, deletions, switch-offs, quits and sweeps.

   | Subset | Scenarios | Broken, 9.1.0 | Broken, record | Better | Worse | More not-ok statuses with the record |
   |---|---|---|---|---|---|---|
   | One profile, cache does not name `llm-router`, v2 kept | 1002 | 35 | 35 | 0 | 0 | 0 |
   | Same, v2 deleted | 384 | 132 | 64 | 74 | 0 | 0 |
   | One profile, user cache names `llm-router` | 1015 | 658 | 656 | 18 | 1 | 186 |
   | Two profiles | 1599 | 1185 | 1185 | 3 | 0 | 0 |

   Better than `v9.1.0`. In the row's own case the leftover LLM Router entry falls from 72 scenarios to 0, with no new break. The same. Every scenario where `v2/config.json` stays, and every two-profile scenario. Worse. Where the user's original cache names `llm-router`, `v9.1.0` already refuses the switch-off (N-2), but once `v2/config.json` is gone it reports ok again. The record keeps the cache marked, so the not-ok status repeats on every later save, sweep and quit, and once it cascaded into a file the user deleted coming back. The remaining breaks in the first row are older kinds outside this row, the same in both builds.
5. **Attack.** The record rule judges nothing by content, and it does what round one said. Its failure comes from the content rule beside it. The cache's matcher counts any reference to the id as LLM Router's (`isManagedZcodeConfigContent` reads `defaultModel`, `lastUsed`, `lastUsedModel` and the provider list), so a user's own original that names `llm-router` is refused as a snapshot. That is the batch 9 lesson again, on the snapshot side. A record of the ids is only safe with a record of what LLM Router wrote under them. Doing nothing is better until N-2 is settled, and the case's weight dropped further with the ZCode source.
6. **Verdict.** Round one stands for the release. Do not build (c) on its own. If ZCode support stays, the VM pass first measures what the current ZCode app reads (N-3). N-1 comes next, then N-2, and only then this row. What would change my mind is a current ZCode that still reads the cache and rewrites or removes `v2/config.json`.

## F-RESTORE-2. The button and the docs sentence on `main`

1. **Re-measure (run).** For OpenCode (`~/.config/opencode/opencode.json`) and Pi (`~/.pi/agent/models.json`), each through the gateway stop path (`restoreTakeoversWhenNoGatewayServes`, with nothing on the gateway port) and through the exit restore (`restoreGlobalProfileConfigsOnExit`), in four cases each, 16 runs:
   - Untouched since the apply. The file comes back byte for byte, with no key under the folder.
   - Edited during the takeover. The user's addition is kept and nothing of LLM Router's stays.
   - No file before LLM Router. The file is removed, with nothing left beside it.
   - The saved config still has the profile on, which is what a refused save leaves. The file comes back byte for byte.
   The Electron quit runs `restoreTakeoversWhenNoGatewayServes` after the gateway stops (`main-app.ts:198`, read). The web server's stop and quit paths call it too (`management-server.ts:562,617`, read).
2. **Where the sentence is wrong.** It says the files of OpenCode, Kilo, Pi, ZCode and Workbuddy come back on a switch-off, a stop and a quit. For ZCode that is false in three cases. With two global ZCode profiles, the switch-off after a second save is refused, and the profile key stays in `cli/config.json` (N-1, run). With a user cache that names `llm-router`, the switch-off is refused and LLM Router's cache entry stays (N-2, run). With `v2/config.json` deleted, LLM Router's cache entry stays under an ok status (F-RESTORE-1). A stop or a quit runs the same restore and fails the same way (harness, run). Also, "stop the gateway or quit to get the file back" lasts until the next gateway start, which applies the profile again (`ensureStarted` then `applyProfileIfServiceRunning`, read). Kilo and Workbuddy were not run.
3. **Verdict.** Round one stands for the button. The sentence needs one qualifier for ZCode, written when N-1 is decided. A suggested text is "For ZCode, a refused switch-off says so, and the file is left as it is."

## F-RESTORE-3. The Codex token command, and `gateway_oauth.credential_export`

1. **Re-measure.** The installed Codex is `codex-cli 0.172.0`, and `0.172.0` is still npm's `latest` for `@openai/codex` (run). GitHub's newest release is `rust-v0.174.0-alpha.9`, published 2026-11-27 (run). The config reference moved. `developers.openai.com/codex/config-reference` now answers 308 to `learn.chatgpt.com/docs/config-file/config-reference` (run). Its `auth` rows match X-2 (read).
2. **What `gateway_oauth.credential_export` is.** Read in the reference and, a second way, in Codex's source (`codex-rs/model-provider-info/src/gateway_oauth.rs` on `main`). `gateway_oauth` is the credential of a gateway that sits in front of a provider. It is either OAuth settings (authorization and token URLs, client id) or `credential_export`, a command that prints one access token, with `args` and `timeout_ms` (default 30000). The token goes in `Authorization: Bearer` unless `delivery` names another header or a cookie. With the default delivery, Codex refuses to combine it with `env_key`, `experimental_bearer_token`, `auth` or `requires_openai_auth`. The release notes name gateway OAuth from 0.166.0 (`rust-v0.166.0`, `0.167.0`, `0.169.0`, read), `credential_export` is in the source at `rust-v0.170.0` and `0.172.0` and absent at `0.165.0` (read).
3. **What the installed Codex accepts (run, config load only).** The `auth` table loads. A `gateway_oauth.credential_export` table loads. Either beside `experimental_bearer_token`, or the two together, is refused with "Header conflict. Codex is configured to send both the model provider credential and the gateway token in the Authorization header". An unknown key inside `credential_export` loads without complaint. `requires_openai_auth = true` with the gateway token delivered in `X-Gateway-Auth` loads.
4. **Which base.** The `auth` table. LLM Router is the provider itself, so its key is the provider credential, which is what `auth` is for. It refreshes on `refresh_interval_ms`, where `credential_export` lists no refresh setting. It exists in the source at `rust-v0.120.0` and `0.134.0` (read), so X-1's oldest-version question is mostly answered without a download. `credential_export` is for a second credential beside the provider's own. Its one use for LLM Router would be a Codex that keeps its ChatGPT login and also sends LLM Router's key in another header, which is a different design from Task 9's.
5. **Task 9's text needs three edits before it runs.** Point the reference at the new URL. Add one row that repeats "Accepted" with `gateway_oauth.credential_export` in place of `auth`, so the owner sees both on the same stub. In the Versions row, record that `auth` is in the source at 0.120.0 and 0.134.0, read and not run, so the download question can close as (a). Do not run Task 9 here.
6. **Verdict.** Stands with that change. Confidence high.

## F-RESTORE-5. The record and the notice rule

1. **Re-measure (run).** A global Claude Code profile over a user `settings.json`. After the apply the profile's `settings-state.json` holds `endpoints: ["http://127.0.0.1:9"]`. After the switch-off it holds `endpoints: []`, `displacedEnv: {}` and `restored: true`, while `settings.json.llmr-original` still exists beside the file. So "a profile's record is kept while a saved original exists" is not what runs. Confirmed.
2. **Is any case worse than the row's rule? Yes, one (run).** The applied file was written back over the restored one, as a dotfiles sync or a copied backup would. A save with the profile off reports "LLMR found nothing to restore" and leaves it. A gateway stop leaves it too. The file holds no key, since Claude Code's settings carry none, so the cost is a Claude Code that points at a gateway that may not answer, until the user edits the file or applies the profile again. Under the row's rule the next pass would have stripped it. That is the trade batch 9 measured, 0 user files changed on a later pass against 247 on the older code, and it is decided.
3. **Verdict.** Stands. Reword the row's first half to the `restored` flag and close it. Round one's note about the same stale sentence in the delivery index still holds.

## F-CODEX-1. A provider with no header

1. **Re-measure (run).** Codex 0.172.0 loads seven forms of a provider `llm-router`: a header, a quoted header, an inline table under `[model_providers]`, dotted keys under `[model_providers]`, dotted keys at the root, quoted dotted keys at the root, and a root inline `model_providers = { ... }`. `v9.1.0` applies over each with an ok status. Codex then refuses five of the applied files with "duplicate key" at LLM Router's `[model_providers.llm-router]`, and the root inline form with "cannot extend value of type inline table with a dotted key". The switch-off restores every original byte for byte.
2. **Correction to round one.** Round one wrote that a headerless provider under any other id is fine. That holds for dotted keys and for an inline table under `[model_providers]`. A root inline `model_providers = { mine = { ... } }` breaks too, whatever the id (run).
3. **Prototype of the refusal (run).** `headerlessCodexProviderTable` in `codex-config-strip.ts` (9 lines) uses the existing statement scanner. It matches an assignment under `[model_providers]` whose key is the id or starts with it, and a root key `model_providers.<id>...` or `model_providers`. `applyCodexProfile` refuses next to the reserved-id check (4 lines). The new test applies five forms and asserts a not-ok status, the message, the original byte for byte, and a Codex folder that holds only `config.toml`. It fails on `v9.1.0` at the first form and passes with the patch. Across the nine forms the refusal covers all six that break and lets the header, quoted header and other-id dotted forms through. Codex loads each refused original unchanged. `npm run test:core` passed, 2551 tests and none failed, and `npm run typecheck` passed (run). Patch `f-codex-1-proto.patch`.
4. **What the scanner would need to see instead.** To merge rather than refuse, it would have to treat dotted keys under `[model_providers]`, root dotted keys and inline tables as the provider's table, and rewrite an inline value when the user's provider is replaced. A restore after an edit would then rewrite the user's inline table, the risk round one named for option (b). The refusal needs none of that.
5. **Attack.** Nobody is worse off than under `v9.1.0`, where the same user gets a Codex that does not start under an ok status. On an upgrade from 9.1.0 a file already doubled is refused at the next apply and restored at the switch-off. The message is wrong for one form: for a root inline table under another id it still names `[model_providers.llm-router]`, so a built version should name the root inline table separately. A file that defines `[model_providers.llm-router.query_params]` with no parent table is refused by Codex before LLM Router touches it ("provider name must not be empty", run), so it is out of scope.
6. **Verdict.** Changed from "build nothing" to "build the refusal" in the remediation release, with that message fix and the docs sentence on `main` extended to the root inline form. Confidence high. Doing nothing stays acceptable, because the trigger needs a rare spelling, but the refusal is cheap and turns a false ok into a true one.

## New findings

- **N-1. Two global ZCode profiles leave the profile key in `cli/config.json` (run).** One profile on, a second off with another `providerId`, two saves, then a switch-off. The status is not ok, "No original ZCode config backup was found", the key stays in `~/.zcode/cli/config.json`, and LLM Router's entry stays in the cache. One profile alone passes. The same run for Codex, OpenCode and Pi passes, though Pi's file is not byte for byte with two profiles (not examined). The file listing shows `cli/config.json.llmr-original-missing` gone. The likely cause is that the off profile's restore finds nothing of its own id and calls `forgetMissingOriginal`, which deletes the marker the on profile's takeover needs (`restoreGlobalConfigFileContent`, the `strip && originalMissing` branch, read). Codex has an `enabledOwnerOfFile` guard for exactly this, and `restoreDisabledZcodeProfile` has none (read). The harness breaks 1185 of 1599 two-profile scenarios on both builds, not all of them by this cause.
- **N-2. A user's ZCode cache that names `llm-router` refuses the switch-off (run).** An original cache whose `lastUsed` or a provider entry uses the id `llm-router`, one apply, a switch-off. The status is not ok, LLM Router's entry and model references stay in the cache, and the user's values are only in `.llmr-original`. No key is involved. Cause read in `zcodeManagedContent`, as F-RESTORE-1 point 5 says.
- **N-3. Current ZCode may ignore all three files LLM Router writes (read, not run).** In the source of 2026-11-23, providers come from `v2/provider_config.json`, and `v2/config.json` and `cli/config.json` are read only to create it once. If that file exists, a takeover has no effect. If it does not, ZCode's first start during a takeover would import LLM Router's provider, `source: "custom"` and the profile key as `apiKey`, into `provider_config.json`, which no LLM Router restore knows about (`legacyZCodeConfigProviderReader.ts` maps `options.apiKey`, the importer keeps custom providers, read). No LLM Router source names `provider_config.json` (run, grep). This is the most important ZCode fact for the VM pass.
- **N-4. The Codex config reference moved** to `learn.chatgpt.com/docs/config-file/config-reference` (run). Links in the plans still use the old host.
