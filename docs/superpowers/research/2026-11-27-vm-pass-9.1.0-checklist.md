# VM pass on the released 9.1.0 app, checklist

**Build.** LLM Router 9.1.0, tag `v9.1.0` at `6596e807`, published 2026-11-27 21:01 UTC with 14 assets (read from the release that day). PRs 149 to 181 are new since 9.0.0.

**What the pass is for.** About thirty PRs merged with checks that only a real app, a real agent CLI or a real login can show. This file is every one of them, read against the code at `v9.1.0`, in the order one sitting can run them. Task 11 of `docs/superpowers/plans/2026-11-27-finish-and-release.md` asks for it.

**Scope, by the owner on 2026-11-27.** New installs only. The upgrade from 9.0.0 is left out, so checks VM-3 and VM-4 are not run. Their text is kept near the end of this file.

**Time.** About 5 and a half hours for the 51 checks on the VM (an estimate, not measured): 40 minutes of setup, 15 for the install, 2 hours 45 for the main branch, 1 hour 45 for the Claude login branch. The checks that need a Grok, Kimi or Pi CLI, WorkBuddy, ZCode or a tiered model can be marked not run without blocking the rest.

**Results.** Mark every check in the table at the end: passed, failed or not run, and what was seen. A failure is a line for the remediation plan. It does not stop the pass.

**Labels.** "Read" means read in the code at `v9.1.0` while writing this. "Seen on 9.0.0" means the pass of 2026-11-24. Nothing here was run.

### Three helper scripts

They print no key. They are already written on the host, in `~/vm-proof/llmr/helpers`, from the text below, and each passed `sh -n` there (run). In the VM, after S1, copy them into the home folder so nothing has to be typed or pasted:

```sh
cp "/Volumes/My Shared Files/vm-proof/llmr/helpers/"vm-*.sh ~/ && chmod +x ~/vm-keys.sh ~/vm-owner.sh ~/vm-takeover.sh && ls -l ~/vm-*.sh
```

The block below is the record of what those three files hold. Use it only if the shared folder is not there.

```sh
cat > ~/vm-keys.sh <<'EOF'
#!/bin/sh
# Each stored key: id, expiry, HTTP status of /v1/models on 3456, and the files that hold it.
DB="$HOME/.llm-router/config.sqlite"
sqlite3 -readonly -separator '|' "$DB" "select id, expires_at, encrypted_key from api_keys order by created_at" |
while IFS='|' read -r id exp key; do
  code=$(printf 'Authorization: Bearer %s\n' "$key" | curl -s -o /dev/null -m 5 -w '%{http_code}' -H @- http://127.0.0.1:3456/v1/models)
  files=$(grep -rlF --exclude='*.sqlite*' -- "$key" "$HOME/.llm-router" "$HOME/.claude" 2>/dev/null | sed "s|$HOME|~|" | tr '\n' ' ')
  echo "$id expires=${exp:-never} status=$code files: $files"
done
EOF
cat > ~/vm-owner.sh <<'EOF'
#!/bin/sh
# Every 10 s for $1 seconds (default 300): the listener on 3456 and its parent. Counts owner changes.
secs=${1:-300}; prev=""; changes=0; end=$(( $(date +%s) + secs ))
while [ "$(date +%s)" -lt "$end" ]; do
  pid=$(lsof -tnP -iTCP:3456 -sTCP:LISTEN | head -1)
  if [ -n "$pid" ]; then pp=$(ps -o ppid= -p "$pid" | tr -d ' '); who=$(ps -o comm= -p "$pp"); else pp=none; who=none; fi
  [ -n "$prev" ] && [ "$pid" != "$prev" ] && changes=$((changes+1)); prev=$pid
  echo "$(date +%T) listener=${pid:-none} parent=$pp $who"; sleep 10
done; echo "owner changes: $changes"
EOF
cat > ~/vm-takeover.sh <<'EOF'
#!/bin/sh
S="$HOME/.claude/settings.json"; D="$HOME/Library/Application Support/Claude-3p"
echo "settings.json: $(grep -o '"ANTHROPIC_BASE_URL": *"[^"]*"' "$S" 2>/dev/null || echo 'no ANTHROPIC_BASE_URL')"
echo "Claude App meta: $(grep -o '"appliedId": *"[^"]*"' "$D/configLibrary/_meta.json" 2>/dev/null || echo 'no appliedId')"
echo "Claude App root: $(grep -o '"deploymentMode": *"[^"]*"' "$D/claude_desktop_config.json" 2>/dev/null || echo 'no deploymentMode')"
EOF
chmod +x ~/vm-keys.sh ~/vm-owner.sh ~/vm-takeover.sh
```

How to read them.
- **A takeover is in place** when `ANTHROPIC_BASE_URL` names `127.0.0.1:3456`, `appliedId` is set and `deploymentMode` is `"3p"`. **It is restored** when the script prints "no ..." three times.
- **The desktop app owns the gateway** when the listener's parent is `.../LLM Router.app/Contents/MacOS/LLM Router`. Any other parent is the CLI service.

The scripts of the last pass in `$S/decisions` do the same reads and still fit 9.1.0 (`10-keys.sh`, `12-owners.sh`, `13-watch.sh`, `30-recorder.sh`, read against the store's schema). `01-get-app.sh` is pinned to 9.0.0. Do not use it for 9.1.0.

### Group A. Clean install (from S0)

#### VM-1. The dmg is the signed build and Gatekeeper lets it open

1. From S0, run `cd $S/v910 && QUARANTINE=1 ./install-check.sh LLM-Router_9.1.0-mac-Apple-Silicon-arm64.dmg`.
2. Approve the macOS first-launch prompt.
3. Read the newest `logs/install-check-*.log`.

- **Pass.** The dmg's sha512 line equals the `sha512` in `latest-mac.yml`. `codesign verify exit 0`. The signature lines show `Identifier=net.matherly.llmrouter`, an `Authority=Developer ID Application` line and the `runtime` flag. The app's `spctl` line says `accepted` and `source=Notarized Developer ID`. `stapler exit 0`. Version `9.1.0`, arch `arm64`. The window opens on onboarding with no red box titled "Service failed to start".
- **Fail.** A checksum mismatch, `rejected` on the app, or the red box. A `rejected` on the dmg's own `spctl` line is not a failure, since only the app is signed (inferred).
- **From.** v8 plan Task 11, the signed-dmg check. **Needs.** Nothing.
- **Then.** Go back to S0. The quarantined app is not fit for another check.

## One read, not a VM step

**Question (F-GATEWAY-19, second half).** Does the gateway fork have a request path that skips the provider hook, so that a marker meant only for the hook would be sent upstream?

**Answer, read.** Yes, one. No path LLM Router uses reaches it.

- **The path.** `checkProviderHealth` in `src/gateway/provider-health-check.ts` builds its request in `buildHealthCheckRequest` from `providerConfig.apikey` and sends it with a plain `fetch`. It resolves no provider plugin and runs no `authenticate` hook. For an Anthropic-type provider it sends `GET <baseurl>/v1/models` with the stored key as `x-api-key`.
- **Its two callers.** The route `POST /manager/providers/health/check` in `src/manager/routes.ts`, and the scheduler in `src/gateway/provider-health-scheduler.ts`, which runs only when `providerHealthCheck.enabled` is true. Its default is false (`parseProviderHealthCheckSchedulerConfig` in `src/config.ts`).
- **Every other upstream path runs the hook.** `callUpstream` has four call sites. The two in `src/gateway/handler.ts` and `src/gateway/openai-json.ts` come after `applyProviderRequestPlugins`. The two in `src/agent/provider-adapter.ts` call the gateway's own address, so they pass through the handler. The WebSocket path runs `applyWebSocketProviderRequestPlugins`. `shouldRunProviderPlugin` can skip a hook that carries `models`, `sourceAdapters`, `sourceRoutes` or `when`, and LLM Router's hook carries none of them (`local-agent-auth-provider-hook.ts`).
- **What would be sent.** The provider's stored key, which for a Claude apps gateway provider is the placeholder `llmr-local-agent-login`. Never a session token. It would go to that provider's own gateway address. The plugin's `auth` block never reaches the fork at all, because `withoutStaticLocalOauthAuth` in `config-compiler.ts` removes it.
- **Whether LLM Router triggers it.** No, as read. No LLM Router source sets `providerHealthCheck` or calls that route. The one manager route it calls is `/manager/config`. The environment variable `PROVIDER_HEALTH_CHECK_ENABLED` would switch the scheduler on in the gateway child if a user's shell set it.
- **Read at.** `~/dev/llmr-gateway`, local branch `fastify-log-controller` at `d35913c`, one commit past `v1.0.22-llmr.4`. Nothing there was changed. Inferred and not read: that the compiled provider entry carries the placeholder as `apikey`.
