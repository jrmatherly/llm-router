# Claude App takeover opt-in and Claude Code token refresh

Decided 2026-10-28 after the claude-multipass incident. Revised 2026-10-28 after a three-model plan review. Two independent changes, one spec, two plans.

## Why

While LLMR runs with an enabled Claude Code profile that has an App entry, it writes `deploymentMode: "3p"` and an applied config-library entry into the shared `~/Library/Application Support/Claude-3p/` dir (`packages/core/src/agents/claude-app/gateway-service.ts`, `syncClaudeAppGatewayConfig`). Claude Desktop reads that dir at every launch (its bundle: `readPersistedDeploymentMode` over `<userData>-3p/claude_desktop_config.json`, `resolve3pForcingSource`), so a Dock launch or an account switcher's `open -a Claude` boots the third-party instance: no claude.ai account, Code tab sessions under `Claude-3p`, inference through LLMR only. PR 48 limited the write to System default profiles. The operator chose a stricter contract: never by default, opt-in per profile.

Separately, LLMR's imported Claude Code provider reads the Keychain item `Claude Code-credentials` on every request (`authenticateClaudeCode` in `packages/core/src/gateway/core-runtime/local-agent-auth-provider-hook.ts`) but never checks `expiresAt` and never refreshes, unlike the Grok and Kimi providers. Under LLMR's `apiKeyHelper` takeover the CLI does not refresh its own login either, so after a switch to a profile saved hours ago LLMR sends an expired token and answers 401 until something else refreshes it.

## Change 1: explicit opt-in for taking over direct Claude App launches

- New optional `ProfileConfig` field `claudeAppTakeover?: boolean` (`packages/core/src/contracts/app.ts`). Absent or `false` means never write the shared `Claude-3p` dir for this profile. The per-profile data dir LLMR launches with (`<settings dir>/.llm-router/claude-app-user-data/<profile>` and its `-3p` sibling) is unaffected: the play button and `llmr <profile>` keep working without the toggle.
- The field must survive every place a profile is rebuilt from a key list: the core loader (`parseProfiles` in `packages/core/src/config/config.ts`), the UI normalizers (`normalizeProfileItem`, `normalizeUnknownProfileItem` in `packages/ui/src/pages/home/shared/profiles.ts`) and the draft round trip. A core test saves and reloads a profile with the flag.
- `claudeAppTakesOverDirectLaunches(profile)` becomes `profile.enabled && profile.agent === "claude-code" && profile.surface !== "cli" && profile.claudeAppTakeover === true`. Scope no longer matters for the App surface; the CLI surface keeps its scope semantics.
- One owner at a time. The shared dir has one content, so at most one enabled Claude Code profile may carry `claudeAppTakeover: true`. `enforceSingleEnabledGlobalProfilePerAgent` (already run on every save in core and UI) also clears the flag on every other Claude Code profile, keeping it on the preferred index when given, else the first. Without this rule a play-button launch of profile B would rewrite the shared dir with B's model while A still shows the toggle on.
- The profile editor shows the toggle directly below Entry mode, outside Advanced settings, only for `claude-code` with surface App or Auto, labelled **Route Claude App launched outside LLMR through LLMR**, with the hint "Also applies to launches from the Dock or an account switcher. Claude App then opens in third-party mode, signed out of claude.ai. Only one profile can have this on." Default off. For a Claude Code profile with surface App, the Effect scope field gets the hint "Applies to the CLI entry. The App entry uses the toggle below."
- Turning the toggle off, disabling the profile, or quitting LLMR restores the shared dir (existing `restoreClaudeAppGatewayConfig` on the no-entry branch of sync). After a crash the dir stays in third-party mode until the next LLMR start; the troubleshooting entry says so.
- Migration: no stored profile has the field, so every existing profile stops taking over after upgrade and the first sync restores the shared dir from the backup the previous version wrote. Release note required. Profiles the UI parses with the old shape keep working (field optional).
- Docs: the field rows and the Effect scope rows in `docs/src/content/docs/en/configuration/agents/claude-code.md` and `docs/src/content/docs/en/configuration/profiles.md`; the troubleshooting entries from PR 48 reworded to name the toggle.

## Change 2: Claude Code OAuth expiry and refresh

- A Claude Code specific token type `ClaudeCodeTokenSet = OAuthTokenSet & { expiresAt?: number; refreshTokenExpiresAt?: number; scopes?: string[]; store: ClaudeCodeTokenStore }` in `packages/core/src/agents/local-providers/claude-code.ts`. `expiresAt` is epoch ms, read from `claudeAiOauth.expiresAt` (Claude Code 2.1.312 stores `expiresAt: 1793249706961`). The shared `OAuthTokenSet` stays as it is: `GrokTokenSet` already declares `expiresAt?: string` and Kimi `expiresAt?: number` in seconds, so a shared field would collide.
- `store` records where the record lives and how to write it back: `{ kind: "keychain", service, account }` or `{ kind: "file", path }`, plus `container: "claudeAiOauth" | "root"`. A record read from the accountless legacy Keychain tier or from a `-custom-oauth` service is readable but never refreshed: the first cannot be written back to the item it came from, the second belongs to an endpoint LLMR does not know.
- `claudeCodeAccessTokenExpired(auth)` is true when `expiresAt <= Date.now() + 60_000`, the same 60 s margin as `grokAccessTokenExpired`. No `expiresAt` means not expired (older records). A record with a refresh token and no access token counts as expired, so it refreshes instead of staying locked.
- `resolveClaudeCodeAuth()` mirrors `resolveGrokAuth`: returns the live token set when not expired; otherwise refreshes once per credential (coalesced by store), persists the result, and when the server rejects the refresh token adopts a token the CLI or Desktop rotated in the Keychain since the read. Rejection means HTTP 401 or 403, or HTTP 400 or 401 with body `error: "invalid_grant"`, which is how Claude Code itself classifies a consumed refresh token.
- Refresh request, from the Claude Code 2.1.312 binary: `POST https://platform.claude.com/v1/oauth/token`, `Content-Type: application/json`, body `{ "grant_type": "refresh_token", "refresh_token", "client_id": "9d1c250a-e61b-44d9-88ed-5944d1962f5e", "scope": "<stored scopes joined by one space>" }`. Response: `access_token`, `refresh_token` (absent means keep the old one), `expires_in` (seconds), optional `refresh_token_expires_in` and `scope`. Through `fetchWithSystemProxy`, 15 s timeout. Env override `LLMR_CLAUDE_CODE_OAUTH_TOKEN_ENDPOINT` for tests, honoured only for a loopback host.
- The refreshed pair is held in memory per credential until the stored record changes. A refresh rotates the refresh token server side, so the old one is never posted again: a failed write retries the write, not the refresh, and a rejected refresh token is remembered and skipped until the record on disk changes.
- Persistence writes the whole record back to where it came from, only when the stored refresh token still equals the one that was posted (compare-and-swap, the same rule Claude Code applies under its `.storage-write` lock); otherwise the stored pair is adopted. Keychain: the line `add-generic-password -U -a "<account>" -s "<service>" -X <hex of JSON>` on the stdin of `security -i`, as Claude Code and claude-multipass do, with argv only when the line exceeds 4032 bytes. Never the record on argv otherwise, never `-w`. File: temp file at mode 0600 in the same directory, then rename. `claudeAiOauth.accessToken`, `refreshToken`, `expiresAt`, and when the response carries them `refreshTokenExpiresAt` and `scopes`, change; `mcpOAuth` and the other keys are kept. A write failure is logged once per store as a fixed message with the exit status, never the caught error text, which would echo the command line.
- Every reader of the raw token uses the resolver: the hook (`authenticateClaudeCode`), the usage connector (`localClaudeCodeAccountCredential`), the compiled plugin defaults (`withClaudeCodeOauthRuntimeDefaults` in `config-compiler.ts`), the probe (`localClaudeProbeToken` in `probe.ts`) and the import (`importClaudeCodeProvider`). The candidate scan stays synchronous and reports a `locked` candidate when the access token is expired and the record has no refresh token.
- Not persisting is not an option: a refresh rotates the refresh token server side, so an in-memory-only refresh would strand the CLI's copy, which is the "OAuth token revoked" failure seen on 2026-10-28 at 18:44.

## Change 2 revisions, 2026-10-29

Decided after a three-model adversarial review (fable, opus, sonnet) of PR 50 and the live check on a throwaway login. Each line amends the Change 2 bullet it names; everything else in Change 2 stands.

- Readers: the auth hook and the import no longer fall back to the stored token when the refresh token was **rejected** (`ClaudeCodeRefreshAuthError`): the hook answers the request with `ok: false` and the error's message (which names `claude /login`), and the import throws it. The fallback to the stored token stays for transient failures (network, timeout, 5xx) and for the usage connector, the compiled plugin defaults and the probe, where a stale token is still the best answer. One exported helper carries the stale-token policy for those three readers; the hook keeps a single try/catch that distinguishes rejection from transient failure; the five hand-written `.catch(() => readClaudeCodeOauth())` copies go.
- Persistence, Keychain: the argv form above 4032 bytes stays (Claude Code itself uses it there), but it is no longer silent. The write logs once per store, fixed text, that the record exceeded the `security -i` stdin limit and went through argv, where `ps` can read it for the write's duration; the providers docs say the same in one sentence. The `security` write runs with a 10 s timeout (`LLMR_CLAUDE_CODE_KEYCHAIN_WRITE_TIMEOUT_MS` overrides it, as the refresh timeout's env does) so a Keychain prompt cannot block the gateway; a timeout is a failed write, logged with the reason `security timed out`. The writer itself asserts the account against `claudeCodeKeychainAccountPattern` and the service against `claudeCodeKeychainServicePattern` before building the `-i` line. The once-per-store write-failure warning re-arms after a successful write.
- Refresh response without `expires_in`: `expiresAt` becomes `undefined` (unknown, so not expired, Claude Code's own reading of a missing field), not the previous value.
- Record reader: only `expiresAt` and `refreshTokenExpiresAt` (camelCase, epoch ms, what Claude Code 2.1.312 writes) are read; the snake-case `expires_at` and `refresh_token_expires_at` aliases are dropped as unverified. `findOauthTokenSet`, dead since the mcpOAuth fix, is deleted. `claudeCodeAccessTokenExpired` is no longer re-exported from `service.ts` (no importer).
- Internal shape, no behaviour change: the per-credential state (in-flight refresh, cached pair with its compare-and-swap baseline and write-retry hold, rejected token, warned flag) lives in one record per store key instead of four module maps; persistence returns the resulting entry instead of a status string, and the refresh call is a pure POST that owns no state. The baseline field is named for what it is (`storeBaseline`: the refresh token the store is believed to hold), not `postedRefreshToken`.
- Tests for the refresh, persistence and the fake Keychain move to their own file; the provider test file had passed 1000 lines.

Open decisions, not in the plan: refusing the Keychain write above the cutoff instead of using argv (strands large records in memory, which this spec rejects); narrowing the rejection table to `invalid_grant` plus 401 so a proxy 403 is not remembered; letting the synchronous candidate scan report a refresh-token-only login as `available`.

## Out of scope

- Any change to claude-multipass.
- Binding the provider to a claude.ai account or showing which account it currently routes to.
- Refreshing the Desktop app's own token cache.
- Taking Claude Code's refresh lock directory. The compare-and-swap closes the write race; the residual window where LLMR and an interactive `claude` both post the same refresh token in the same minute is stated in the PR.
