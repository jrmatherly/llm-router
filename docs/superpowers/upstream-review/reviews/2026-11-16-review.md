## Follow-up research on the three owner decisions (2026-11-16)

### Row 28: `~/.claude.json`

Recommendation: take the environment half only, and never write `~/.claude.json`.

- Claude Code 2.1.326 keeps its global state at `<CLAUDE_CONFIG_DIR or home>/.claude.json`. With the variable set to `~/.claude` it uses `~/.claude/.claude.json`. Read from the installed binary's strings, not from the docs, which do not say.
- `autoCompactWindowsCache` is Claude Code's own key. Claude Code refills it from the bootstrap response field `auto_compact_windows`, which the gateway already serves (lead-checked: `gateway/features/model-discovery.ts:123-126`). So LLMR does not need to write it for a default-home profile.
- claude-multipass rewrites `oauthAccount` in `~/.claude.json` while holding three lock files, and never sets `CLAUDE_CONFIG_DIR` (lead-checked: `bin/claude-multipass:173`, `:685`, `:2082-2088`). LLMR's write is atomic but takes no lock, so writing that file could revert a switch.
- The dotfiles neither track nor template either file and export the variable nowhere (lead-checked for `tilde/`).
- On the owner's machine `~/.claude/.claude.json` holds one key, LLMR's cache, written 2026-10-28. Claude Code has never used it (lead-checked: key names only).
- The port should also cover three places upstream missed: `agents/claude-app/launch.ts:64`, `profiles/launch-service.ts:1356` and the reader at `agents/codex/cli-middleware-runtime.ts:6525`.
- Not verified: that Claude Code fetches the bootstrap from the gateway under `apiKeyHelper` auth and stores the windows. A launch under a throwaway home settles it.

### Row 27: Codex desktop identity

Recommendation: redesign, do not port. Take the identity default now as a profile setting, and leave the TLS listener until a live check shows the desktop app needs it.

- Today the runtime reads a ChatGPT login once at app-server start, falling back to `~/.codex/auth.json` (lead-checked: `cli-middleware-runtime.ts:4752-4762`). The only opt-out is an environment variable nothing sets.
- The desktop app receives the real access token through `getAuthStatus` (lead-checked: `:4852-4858`), and attaches it to `http://localhost:8000`, which the responder serves on `127.0.0.1` only (lead-checked: `app-net-responder.ts:150-157`, `:252`).
- A token within 30 seconds of expiry is rejected (lead-checked: `:4816-4820`), so the same profile is personal or synthetic depending on the token's age at launch.
- Model calls do not carry the ChatGPT token; they use the gateway token.
- Proposed shape: a `ProfileConfig` field, isolated by default for `llmr` and `custom` scope, visible in the profile UI. No `CODEXL_*` names (D-5), no legacy-auth quarantine (D-9). Per-call auth reload and routing injection wait for the `.cjs` move (D-7).
- If TLS proves necessary: generate the key in memory per process and never store it. Upstream stores a long-lived key, and Chromium's `--ignore-certificate-errors-spki-list` trusts that key for any host.
- Not verified: whether the closed-source desktop app requires an HTTPS `backendOrigin`. No desktop build is installed on the owner's machine; the CLI is 0.169.0.

### F-C12 is settled by this research

The Codex source maps `refresh_token_reused` to "your refresh token was already used" and stores a new refresh token when the response carries one (lead-checked: `openai/codex`, `codex-rs/login/src/auth/manager.rs:236`, `:1799`, `:1870`). Refresh tokens rotate and a reused one is rejected. LLMR copies the access and refresh tokens out of `~/.codex/auth.json` into a provider (lead-checked: `agents/local-providers/codex.ts:297-316`) and refreshes with them, so one LLMR refresh can invalidate the login the user's own Codex CLI holds. CG-7 keeps the rotated token in memory only. It needs a redesign before it lands: re-read `auth.json` and let Codex own the refresh.

## Re-check of the three owner decisions (2026-11-17)

One read-only research pass per decision, then the lead re-read the code behind each claim that changes a recommendation. Upstream had no commit past the watermark on this date. The owner has not decided. Nothing below was run in an app: every "not verified" needs the live check named beside it.

### A finding that reaches past row 29: the host pipeline is not always in the request path

`gateway-service.ts` has two runtime modes (`shouldUseSingleGatewayRuntime`, `singleGatewayRuntimeBlockers`). With no blocker the gateway child binds the public port with the public keys, the host server does not listen, and `GatewayRequestPipeline` never sees a request. The blockers are an active router fallback, proxy, network capture, context archive, media tools, browser automation MCP, a plugin route or request transform, API key limits, and a gateway build without router-plugin support. The defaults in `default-config.ts` set none of them (`fallback.mode: "off"`, proxy, context archive and media tools off), so a default install runs in single mode. Lead-checked by reading; not measured by a run.

So every fix that lives in the host pipeline applies only in compatibility mode. That covers row 2 (PR 82, the terminal frame for a truncated stream) and the requested-model line of row 17 (PR 86). The entries above for those rows do not say this. The PR 82 test drives a stand-in HTTP server, not the gateway child.

### Row 28: `~/.claude.json`

Recommendation unchanged: take the environment half, never write `~/.claude.json`. One recorded reason is probably wrong, and the port should do slightly more than upstream.

- Probably wrong: "Claude Code refills `autoCompactWindowsCache` from the gateway's bootstrap response, so LLMR need not write it." Read from the minified Claude Code 2.1.326 binary by the research pass: under API-key auth the bootstrap call goes to Anthropic's own base URL and ignores `ANTHROPIC_BASE_URL`; only the federation (WIF) path uses the gateway. LLMR defaults to `api-key-helper` (`auth-mode.ts`, lead-checked). So a default-home profile loses LLMR's compaction windows and falls back to Claude Code's defaults, unless the model carries the `[1m]` suffix LLMR already adds. The shared-home spec accepted that cost (`specs/completed/2026-11-01-claude-code-shared-home-launch.md`). Not verified by a run.
- Also wrong: "the docs do not say where global state lives". They do now (`claude-directory.md`, `troubleshoot-install.md` in the local docs).
- The user-visible bug today: `claudeCodeHomeEnv` exports `CLAUDE_CONFIG_DIR` for every profile that is not shared-home (lead-checked). A global-scope profile on `~/.claude` therefore runs against `~/.claude/.claude.json` while plain `claude` uses `~/.claude.json`, so the wrapped session has no onboarding state, personal MCP servers or project trust, and uses a different Keychain entry. claude-multipass refuses to save or switch a login in that environment.
- New: Claude Code writes `autoCompactWindowsCache` itself after each bootstrap, so a write by LLMR into `~/.claude.json` would be overwritten by the next plain `claude` start. Upstream's write half would not even hold.
- New: a shared-home profile still gets the cache written into its generated home (`service.ts`, the unconditional call to `writeClaudeCodeAutoCompactWindowsCache`), which Claude Code never reads. A dead write.
- returnofthemac (the dotfiles repository) and claude-multipass: neither is disturbed by the environment half. multipass rewrites `oauthAccount` under three locks; the dotfiles tools only read `${CLAUDE_CONFIG_DIR:-$HOME/.claude}`.
- Proposed port: the environment half, the three places upstream missed, and no cache write for the default home or a shared home. A later option: default to WIF so the bootstrap reaches the gateway and Claude Code stores the windows itself; that needs the live check.
- Live check, not run: a throwaway `HOME` with `LLMR_INTERNAL_HOME_DIR` set inside it (both, or the real home is rewritten), start the gateway there, apply a global profile, launch its wrapper with `--debug`, then read the `[Bootstrap]` lines, the gateway's log for `GET /api/claude_cli/bootstrap`, and `autoCompactWindowsCache` in that home's `.claude.json`. Repeat with the auth mode set to `wif`.

## Open follow-ups that need research and a plan

The owner asked on 2026-11-16 that these not be lost. Each needs its own research pass and then an implementation plan written with the `superpowers:writing-plans` skill. None is started.

1. **The proxy service's plugin mode forwards every client header to the plugin's target.** `createForwardHeaders` in `packages/core/src/proxy/service.ts` copies every header except the hop-by-hop ones, cookies and `cf-*` included, and in plugin mode sends them to the plugin's `targetUrl`. Found by the PR 75 review (path 7 of the twelve it traced). `plans/completed/2026-11-16-audit-core-gateway.md` reserves `createForwardHeaders` for CG-9 and the surrounding code for CG-2, so the research must start from those two plan sections and decide whether `isFrontDoorHeader` (`gateway/internal/front-door-headers.ts`) applies there, and what a plugin target is entitled to receive.
2. **A statically configured route rewrite that sets a credential or front-door header is dropped at the provider boundary without a message.** `compileConfiguredRouteRewrite` (`packages/core/src/routing/rewrite.ts`) does not protect headers, so a configured rule may set `authorization`, `cookie`, `cf-*` and the rest. Rewrites write into the inbound request headers, which `mergeUpstreamProviderHeaders` treats as client headers and drops. The rule validates, appears to work, and has no effect. Older than PR 75. The research must settle what a configured rewrite is for (the test "dynamic script rewrites cannot mutate protected headers without breaking trusted static config" says static config is trusted), whether such a header should reach the provider, be rejected at validation, or be reported as a diagnostic, and how it relates to provider `headers` config, which is the supported way to give a provider a header.
